Pipelines v2

Pipeline centralizado para todos os projetos da Bankme.
WIF · GCP Secret Manager · Promote, não rebuild · Canary + Rollback

✓ Sem GCP_SA_KEY ✓ Secrets nunca saem do GCP ✓ Imagem de staging = produção ✓ Rollback em 1 clique

← → para navegar · clique nas bolinhas · swipe no celular

Visão geral

Fluxo completo do pipeline

Feature branch → PR aberto
cicd-pull-request.yml → validate-permission · typecheck · lint · test · build · audit · SonarCloud
PR mergeado em develop → Deploy automático
deploy-develop.yml → build Docker → push Artifact Registry → deploy Cloud Run (develop)
GitHub Release publicada (ex: v1.2.0) → Deploy automático em staging
deploy-staging.yml → build Docker → push AR com tag da versão → deploy Cloud Run (staging)
Senior aciona deploy manual → Produção
deploy-production.yml → busca digest de staging → copia para AR de produção → deploy (promote, não rebuild)
Canary opcional após produção
manage-traffic.yml → canary X% → release-100% → ou rollback para revisão anterior
Hotfix → hotfix/* mergeado em main
deploy-hotfix.yml → build + push para AR de staging com tag hotfix-* (sem deploy automático) → Senior promove via deploy-production.yml

Como funciona

Versionamento

Cada projeto referencia o infra-pipelines com @v1.

# Em cada workflow do projeto:
uses: bankme-tech/infra-pipelines-v2/.github/workflows/build-and-deploy.yml@v1
Pense em v1 como um ponteiro fixo. Quando você atualiza o infra-pipelines e quer que todos os projetos recebam a mudança, move o ponteiro:
# Após commit e push no infra-pipelines:
git tag -f v1 && git push origin v1 --force

Todos os projetos passam a usar a versão nova automaticamente na próxima run.

Quando a mudança é grande — crie uma tag nova

git tag v2 && git push origin v2
# Cada projeto migra ajustando @v1 → @v2 nos seus workflows no seu tempo
Por que não usar @main? Qualquer commit — até experimental — chegaria a todos os projetos instantaneamente. Com @v1 você controla exatamente quando uma mudança entra em vigor.
Passo 1

Configurar o GCP — por ambiente

Execute uma vez para cada ambiente: develop, staging, production.

# Clonar e preparar
git clone https://github.com/bankme-tech/infra-pipelines-v2.git
cd infra-pipelines-v2 && chmod +x scripts/*.sh

# develop
./scripts/setup-gcp.sh \
  --project   bankme-frontend-dev --env develop \
  --region    us-central1 --gh-org bankme-tech --gh-repo bankme-frontend

# staging (mesmo comando com --project e --env diferentes)
./scripts/setup-gcp.sh --project bankme-frontend-stg --env staging ...

# production — adicionar --staging-project para o promote funcionar
./scripts/setup-gcp.sh \
  --project         bankme-frontend-prd --env production \
  --staging-project bankme-frontend-stg ...
O script cria: Service Account · WIF (sem chave) · Artifact Registry · roles IAM (run.admin, artifactregistry.writer, secretmanager.secretAccessor) · vinculação WIF←SA

Ao final, o script imprime os valores para usar no Passo 2.

Passo 4

Adaptar o environments.yml

service-name: meu-projeto   # Cloud Run + AR
repository:   meu-projeto

environments:
  develop:
    resources:
      memory:        512Mi
      cpu:           '1'
      min-instances: 0   # 0 = sem custo ocioso
      max-instances: 1
      # cpu-allocation: always  # para workers
    build:
      node-version: '20'
    runtime-env:          # variáveis NÃO-sensíveis
      NODE_ENV:  production
      API_URL:   https://api.dev.ex.com
    runtime-secrets:      # GCP Secret Manager
      AUTH0_SECRET: meu_proj-AUTH0_SECRET:latest
      DATABASE_URL: meu_proj-DATABASE_URL:latest
    # Para PostgreSQL com SSL:
    # volume-secrets:
    #   '/secrets/pg-ssl-ca/server-ca.pem': PG_SSL_CA:latest

runtime-env

Variáveis não-sensíveis. URLs de APIs, feature flags. Ficam em texto puro no YAML — diferem por ambiente.

runtime-secrets

Secrets do GCP Secret Manager. Formato: prefixo-NOME:latest. O Cloud Run os lê na inicialização do container.

volume-secrets

Certificados SSL e arquivos montados no disco. Necessário para PostgreSQL com SSL. Usado em api-oracle, api-bifrost, api-data-warehouse.

Infra GCP (project-id, region, WIF) fica nos GitHub Environment Variables — não no YAML.
Passo 6

Criar os secrets no GCP Secret Manager

O script lê o environments.yml e cria todos os secrets com valor CHANGEME.

# Rodar dentro do diretório do projeto, para cada ambiente GCP
/caminho/infra-pipelines-v2/scripts/setup-secrets.sh --project bankme-frontend-dev
/caminho/infra-pipelines-v2/scripts/setup-secrets.sh --project bankme-frontend-stg
/caminho/infra-pipelines-v2/scripts/setup-secrets.sh --project bankme-frontend-prd

Preencher valores reais

Via Console GCP:

console.cloud.google.com/security/secret-manager?project=bankme-frontend-dev

Via CLI:

echo -n "valor-real" | gcloud secrets versions add NOME \
  --project=bankme-frontend-dev --data-file=-

O pipeline funciona com CHANGEME

O deploy roda sem erros de infraestrutura. A aplicação pode falhar no runtime (Auth0, banco) até os valores reais serem preenchidos.

Mesmo nome, valores por ambiente

meu-projeto-AUTH0_SECRET existe nos 3 projetos GCP com valores diferentes para cada ambiente.

Dúvidas frequentes

Erros comuns e soluções

!
"Permission denied on secret"

O SA não tem secretmanager.secretAccessor.

gcloud projects add-iam-policy-binding SEU_PROJETO \
  --member="serviceAccount:github-deployer@SEU_PROJETO.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
!
"rejected by the attribute condition" — WIF

O ref ou repositório não bate com a condition do provider. Verifique:

gcloud iam workload-identity-pools providers describe github-provider \
  --workload-identity-pool=github-pool --project=SEU_PROJETO --location=global \
  --format="value(attributeCondition)"
!
"ALREADY_EXISTS: Revision ... already exists"

Uma revisão falhou anteriormente com o mesmo nome. Delete o serviço Cloud Run e reimplante.

!
"Permission denied" ao fazer docker pull no promote

O SA de produção não tem leitura no AR de staging. Re-execute:
./setup-gcp.sh --env production --staging-project SEU_STAGING

?
validate-permission falha mas o CI passa

Comportamento esperado — o dev não está no time seniors. O merge só é bloqueado após branch protection (Passo 9).

Migração de projetos existentes

O que muda na migração para v2

Para projetos que já usam o bankme-tech/infra-pipelines antigo com GCP_SA_KEY.

Antes (infra-pipelines antigo)Depois (v2)
Auth GCPGCP_SA_KEY — JSON no GitHub SecretWIF — sem nenhuma chave armazenada
Config parserload-env-config action (depende do repo)Python inline — zero dependência externa
Infra no YAMLgcp-project-id, gcp-region, gcp-registry no environments.ymlSomente nos GitHub Environment Variables
App secretsGCP Secret Manager via runtime-secretsIgual — mesma estrutura, mesmos secrets
Deploy produçãoRebuild completo da imagemPromote — copia digest de staging (imagem idêntica)
Projetos com SSL certificates (api-oracle, api-bifrost, api-data-warehouse) — o v2 suporta nativamente via volume-secrets no environments.yml. Os secrets no GCP Secret Manager não mudam.
Migração — passo a passo

Como migrar um projeto existente

1
Configurar WIF no GCP (Passo 1 deste guia)
./scripts/setup-gcp.sh --project SEU_PROJETO --env develop ...

Mantenha o GCP_SA_KEY como backup até validar que o WIF funciona.

2
Adicionar variáveis GCP nos GitHub Environments (Passo 2)

O secret GCP_SA_KEY pode coexistir — os novos workflows não o usam.

3
Substituir os workflows pelos templates
cp /caminho/infra-pipelines-v2/templates/.github/workflows/*.yml .github/workflows/
cp /caminho/infra-pipelines-v2/templates/.github/CODEOWNERS .github/
cp /caminho/infra-pipelines-v2/templates/sonar-project.properties .
4
Atualizar o environments.yml para o novo schema

Remover: gcp-project-id, gcp-region, gcp-registry
Manter: runtime-secrets e volume-secrets — compatíveis sem mudança.

5
Commit, testar (Passos 7 e 8) e remover o GCP_SA_KEY

Após validar que o pipeline funciona via WIF, delete o GCP_SA_KEY do GitHub Secrets.
